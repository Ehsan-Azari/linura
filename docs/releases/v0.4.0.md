# v0.4.0 — durable transaction and recovery foundation

**Status:** implementation complete; publication evidence is established only by the protected release lifecycle.
**Claim class:** Experimental
**Supported platform profiles:** none

## Outcome

v0.4.0 proves an Experimental durable reviewed-authority transaction and recovery foundation on top of the v0.3 review/approval boundary, without adding a supported executor or a Linura-managed external machine effect.

The qualified authority path is:

```text
authenticated principal + reviewed plan + current authoritative observation
→ Control-owned prepare revalidation
→ immutable durable transaction/generation binding
→ fresh handoff-time principal/observation/policy/risk/approval revalidation
→ durable Prepared → Indeterminate CAS
→ one-shot process-local non-reconstructible dispatch permit
→ authoritative recovery classification
→ Verified / RecoveryBlocked / explicit no-effect N+1 reprepare
→ verified commit metadata + append-only authenticated audit
```

No v0.4 path invokes an executor. The durable handoff and recovery machinery exists to close authority, crash, concurrency, integrity and storage-recovery boundaries before executor qualification begins in v0.5.

## User-visible capability

v0.4.0 does not add a supported apply/execute/mutate product surface. Existing Experimental observation, deterministic plan-preview and plan-review capabilities remain available. The new transaction/recovery foundation is an internal authority substrate exercised by deterministic tests and repository-owned qualification.

A durable transaction ID, generation, `Prepared`, `Indeterminate`, `Verified` or committed record is evidence about the authority lifecycle; none is a public mutation credential. A process-local dispatch permit is sealed, non-cloneable, non-serializable, non-persistable and non-reconstructible after restart, and v0.4 has no executor that can consume it to change Linux.

## Implemented scope

- Persistence-neutral `linura-transaction` domain with typed transaction/generation identities, deterministic domain-separated authority bindings, immutable generation history, idempotency, transition rules and recovery serialization.
- Control-owned non-cloneable transaction signer; persistence receives only verification authority and cannot mint trusted Control requests or dispatch permits.
- Current authenticated-principal binding plus prepare/handoff/recovery revalidation of authoritative observation, trusted review, policy/risk provenance and required approval.
- Signer-authenticated validity windows enforced after SQLite write serialization so lock waits cannot extend expired authority.
- Restart-safe handling of durable `Prepared`, sticky `Indeterminate`, durable verified commit material, resume/commit and explicit no-effect recovery into exactly one next generation.
- SQLite/WAL persistence with `synchronous=FULL`, application/schema identity, versioned repository-visible migration identity, immutable migration ledger and bounded live-schema validation.
- Separately provisioned `SqliteIntegrityKey` authenticating retained transaction, generation and audit records; raw writers can alter bytes but cannot mint valid keyed integrity tags.
- Bounded persisted-input materialization, aggregate capacity checks, logical audit reservations and physical recovery reservations.
- Same-filesystem physically allocated recovery reserve with crash-tail reconciliation, regular-file/path/inode/device/link validation and fail-closed replacement/symlink handling.
- Non-mutating database identity/schema preflight before any persistent journal-mode transition, preventing an unrelated SQLite database from being modified during rejected open.
- Exact-source regressions for authority substitution, raw-persistence tampering, forged/replaced history, restart/resume, CAS races, stale/mixed evidence, key lifecycle, capacity exhaustion, real ENOSPC recovery and durability faults.

## Authority and security boundary

Models, agents, transports and ordinary callers remain untrusted proposers. `linura-control` owns trusted prepare, handoff, recovery and commit orchestration. Persistence verifies authenticated requests and retained records but does not own policy, approval, principal authentication or authority minting.

Policy `Allow`, approval evidence, a reviewed plan, transaction ID, generation number, durable `Prepared`/`Indeterminate`/`Verified` state or audit row does not authorize a Linux mutation. v0.4 adds no public `apply`, execute or mutate API, no generic privileged command surface, no Polkit grant, no supported executor integration and no Linura-managed external effect.

Raw filesystem/database writers can physically modify SQLite bytes. v0.4 protects retained authority history by keyed record authentication, schema/migration identity, immutable-history checks and fail-closed validation. It does not claim that an attacker able to coherently roll back the entire authority database/filesystem/VM snapshot can be detected without a future independently protected monotonic anchor/restore protocol.

## Platform and hardware scope

No Linux distribution, desktop/headless profile, machine class, hardware tier, virtualization profile or fleet environment is supported by the v0.4.0 product claim.

Repository qualification uses disposable Ubuntu 24.04 LTS amd64 QEMU guests and explicitly exercises real loop-mounted ext4 ENOSPC recovery plus SQLite/WAL fault scenarios. Those environments are evidence fixtures, not supported Linura platform profiles.

The durability claim is limited to the named local-filesystem/storage assumptions that honor the locking and sync behavior exercised by qualification. `PRAGMA synchronous=FULL` is part of the design but is not presented as a universal hardware/storage durability guarantee.

## Persistence, migration and upgrade

v0.4.0 introduces the first release-qualified local durable authority database for transaction/recovery state. The SQLite adapter carries explicit application/schema identity, repository-visible versioned migration identity, immutable migration-ledger verification, bounded schema validation and fail-closed handling of corruption, unsupported newer schema and migration mismatch.

Durable idempotency is scoped to one monotonic authority-database history. Exact retained generations are immutable and one stable current-generation/state-version serialization point governs mutually exclusive recovery outcomes. The store maintains bounded authenticated audit history and explicit logical/physical recovery reservations rather than silently evicting authority history under capacity pressure.

An unrelated or unidentified existing SQLite database is rejected before Linura makes a persistent journal-mode change. A genuinely empty unidentified database can be initialized transactionally and restartably.

## Recovery and rollback

`Indeterminate` is sticky across restart and never becomes retry authority merely because a process restarted or a permit was lost. Recovery requires fresh authoritative re-observation and current authority revalidation.

Authoritative intended-state evidence may advance only the exact current indeterminate generation to `Verified`; conflicting evidence may advance only that exact generation to `RecoveryBlocked`; ambiguous/stale evidence leaves it indeterminate. Authoritative no-effect evidence can permit explicit current-authority re-establishment and exactly one N+1 `Prepared` generation while retiring N atomically; it does not itself grant retry authority.

Real loop-mounted ext4 qualification proves the repository's recovery reserve can release same-filesystem space under ENOSPC so a nonterminal generation can reach a safe terminal outcome, survive process reopen and survive filesystem unmount/remount validation.

Coherent whole-database/filesystem/VM-snapshot rollback remains unsupported and is not claimed detectable in v0.4 without an external monotonic anchor/restore protocol.

## Compatibility boundary

Product version `v0.4.0`, D-Bus generation `Control1`, checked `*.v1` schemas and SQLite authority-store schema/migration version are independent version axes. All newly introduced v0.4 contracts remain Experimental and may evolve coherently under the repository's contract-stability rules.

The new durable transaction substrate does not revive superseded provider-owned/executable planning or create a compatibility path around the canonical v0.2/v0.3 plan/review lineage.

## Known limitations and unsupported states

- No executor is release-qualified or invoked by v0.4.
- No public apply/execute/mutate API or generic privileged command authority exists.
- No supported managed external effect exists; v0.6 remains the first milestone allowed to publish one.
- A process-local dispatch permit cannot be reconstructed after restart; an indeterminate operation must recover from authoritative post-state instead of blind replay.
- Complete coherent authority-database/filesystem/VM snapshot rollback is not internally detectable or supported without a future independent monotonic anchor/restore protocol.
- Raw storage writers can physically change bytes; integrity guarantees are detection/fail-closed guarantees for retained authenticated records, not filesystem access prevention.
- `synchronous=FULL` and the qualified ext4/QEMU fixtures do not imply arbitrary hardware/storage durability.
- No Linux distribution, desktop/headless profile, machine class, physical hardware tier, virtualization profile or fleet target is supported by this claim.
- No natural-language/model interpretation, First Boot, persistent Linura Library or complete eleven-stage managed-mutation lifecycle is release-qualified.

## Explicit non-goals

v0.4.0 deliberately does not claim:

- production readiness or a supported installable Linura operating system;
- a privileged executor or independent post-effect verifier;
- Polkit authority, privileged credential acquisition or generic shell execution;
- public apply/execute/mutate or supported package/service/network/storage/desktop mutation;
- any supported Linura-managed external machine effect;
- complete eleven-stage managed mutation;
- agent/model execution authority or durable agent authority;
- supported Linux distribution, machine class, hardware or virtualization profile;
- transparent coherent database/filesystem/VM-snapshot rollback recovery;
- universal durability from SQLite `synchronous=FULL` alone.

## Artifacts and supply-chain evidence

Trusted Release Proof builds the exact selected protected-main release source into the repository's sealed release payload and independently reproduces required distributable binaries before promotion. The payload must include source/version identity, frozen `RELEASE_NOTES.md`, checksums, SPDX SBOM, release evidence, build-environment data and repository-defined provenance/attestation.

Artifact presence does not expand the v0.4 product claim. Workspace executor/bootstrap/update binaries remain scaffolding or future-qualification components unless independently promoted by a later milestone; they are not evidence of supported mutation or installation in v0.4.

## Publication evidence

Publication evidence exists only after the reviewed release-preparation tree is followed by a mechanically validated metadata-only release-authorization commit whose sole parent is that reviewed source and whose Git tree is identical to it. The authorization commit records the reviewed source/tree only in commit metadata through `Reviewed-Source` and `Reviewed-Tree`, avoiding self-referential tracked evidence.

Trusted Release Proof must then validate that intent, rerun mandatory v0.4 qualification, build and independently reproduce the exact source, seal the evidence, and hand the proven bytes to promotion without rebuilding. Final publication is tag-last. Independent Release Verification must re-download and verify the published release before the repository roadmap is advanced from v0.4 to v0.5.

A merged implementation PR, green release-preparation PR, metadata-only authorization commit or successful proof job alone is not proof that v0.4.0 is released.

## Next-version handoff

v0.5.0 may build on this durable reviewed-authority transaction/recovery substrate to qualify one narrow privileged executor and a separate verifier under disposable qualification authority only. That qualification must not turn v0.5 into supported managed mutation.

The v0.4 durable transaction, generation, audit or dispatch-permit semantics must remain inputs to the future execution boundary rather than becoming standalone execution credentials. v0.6.0 remains the first milestone permitted to integrate and publish a bounded supported Experimental managed external effect.
