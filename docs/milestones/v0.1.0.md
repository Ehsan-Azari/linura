# v0.1.0 — authoritative observation and causal graph

**Status:** implementation complete; publication pending protected release qualification
**Target claim class:** Experimental

## Goal

Prove that Linura can authenticate a local caller, obtain authoritative read-only Linux state through provider contracts, represent that evidence in the system graph, and expose it through deterministic non-privileged clients.

This milestone moves Linura from architecture/bootstrap to its first real machine observation. It intentionally performs no privileged Linura mutation.

The milestone was originally tracked as `v0.0.1`. Before publication it was renumbered to `v0.1.0` to comply with Linura's pre-1.0 Semantic Versioning policy: a new externally testable end-to-end capability slice is a minor milestone, while a `v0.MINOR.PATCH` version is reserved for compatible repairs to an already-published minor line.

## Required capabilities

1. Session D-Bus service boundary for `org.linura.Control1`.
2. Caller credentials bound to a typed `Actor`; caller identity cannot be supplied as an unauthenticated client claim.
3. Provider registry/capability discovery with explicit unavailable/degraded states.
4. Read-only systemd observation through the native systemd interface.
5. Read-only NetworkManager observation through the native NetworkManager interface.
6. Observation envelopes with provider identity, resource identity, freshness and authority semantics.
7. Population of observed resource/capability nodes and evidence edges in the system graph.
8. `linuractl observe`, `graph`, `capabilities` and evidence-only `explain` operations over the public SDK/protocol boundary.

## Trust-boundary invariants

- `linurad` remains unprivileged.
- No generic shell or privileged executor is introduced into the observation path.
- Provider observation is authoritative for current machine state; persisted or client-supplied state cannot override it.
- Unknown, stale, malformed or mismatched observations are explicit and cannot be promoted to trusted current state.
- D-Bus caller identity is derived from the transport/OS boundary.
- An AI/model provider is not required for any v0.1.0 capability.
- Read-only observation must not create an implicit mutation authority path.
- Resolving an explicitly named inactive systemd unit may ask systemd to `LoadUnit`; this loads the installed unit definition into the manager so native properties can be observed, but does not start the unit or modify its unit file.

## Implementation scope

- D-Bus transport and caller-credential extraction.
- Provider registry and health/support reporting.
- systemd and NetworkManager observer implementations.
- Observation freshness/identity validation.
- System-graph population from observed evidence.
- Deterministic CLI/SDK query surfaces.
- Unit, contract, integration and disposable-VM observation fixtures.
- Reproducible exact-source disposable-VM release qualification using a dated checksum-pinned base image, ephemeral cloud-init identity and machine-readable evidence.

## Required acceptance evidence

- Canonical Rust formatting, clippy and workspace tests on exact source.
- Repository/tooling checks and CodeQL/Security gates.
- Negative tests for caller-identity spoofing, provider/resource mismatch, malformed observation and stale evidence.
- Disposable VM acceptance proving systemd observation against a controlled installed unit.
- Disposable VM acceptance proving the unit's out-of-band active → inactive transition is reflected by a subsequent authoritative read even after systemd garbage-collects the inactive loaded-unit object.
- NetworkManager observation where the acceptance image exposes the service; unavailability remains explicit when the service is absent.
- No privileged Linura code path required to pass the milestone. Fixture-only `sudo` in the disposable guest creates and removes the external systemd test unit and installs exact-source test binaries.
- Trusted Release Proof, independent byte-for-byte reproduction, provenance attestation, promotion and publication verification before the public release is accepted.

## Explicit non-goals

v0.1.0 does not:

- execute managed system mutations;
- introduce Polkit or a supported privileged executor path;
- persist desired state or durable prepare/commit transactions;
- claim a supported desktop, distribution profile or hardware configuration;
- use an LLM to interpret intent;
- implement First Boot configuration as a supported release capability;
- claim production readiness.

## Exit criteria

- [x] All required read-only capabilities are implemented through the public control/protocol boundaries.
- [x] Caller identity is authenticated and tested against spoofing.
- [x] systemd and NetworkManager observations have explicit freshness/authority semantics.
- [x] Observed evidence populates queryable system graph state.
- [x] Disposable VM acceptance proves representative observation and out-of-band change visibility.
- [x] Exact-source CI, Security and CodeQL are green for the completed implementation baseline.
- [x] Known limitations/unsupported observation states are documented in the frozen release contract prepared with this milestone closure.
- [x] `docs/releases/v0.1.0.md` is frozen with canonical PR/full-SHA traceability before tagging.

## Release handoff

The v0.1.0 release contract may claim **Experimental authoritative read-only observation** only for the providers and disposable-VM evidence actually proven. It must explicitly state that no privileged managed mutation or supported platform/hardware profile is included.
