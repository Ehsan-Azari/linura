# v0.4.0 — durable transaction and recovery foundation

**Status:** planned
**Target claim class:** Experimental

## Goal

Prove that Linura can carry the exact v0.3 reviewed authority subject and complete authoritative-observation binding across process restart into a durable prepare/pre-dispatch/recovery/verified-commit record **without granting execution authority or performing a managed external effect**.

v0.4 closes the authority-to-durability and pre-dispatch crash/concurrency boundaries needed before privileged executor qualification can begin in v0.5.

## Required capabilities

1. A persistence-neutral durable transaction domain owns typed transaction identity, immutable per-generation exact authority-binding material, transaction state transitions, recovery decisions and repository contracts.
2. A local SQLite/WAL adapter implements those contracts with transactional migrations, explicit application/schema versioning, migration checksum verification, `synchronous=FULL`, foreign keys and fail-closed integrity checks.
3. Durable request idempotency is namespaced by authenticated principal + request ID and survives database/process reopen within one monotonic authority-database history.
4. Same idempotency key + exact authority binding for the current `Prepared` generation returns the existing transaction/generation; changed binding through the normal prepare/request path is rejected as conflict.
5. One stable transaction identity retains an append-only sequence of immutable generation records. A later recovery generation never rewrites or rebinds an earlier generation.
6. A new generation with changed current authority material may be appended only by the explicit Control-owned recovery path from the exact expected `Indeterminate` predecessor after authoritative no-effect evidence and full current policy/observation/approval re-establishment.
7. `linura-control` revalidates the current trusted policy review, complete authoritative observation freshness/material and any required approval at prepare time and creates the durable binding from trusted canonical material.
8. The prepare binding covers principal, request, plan, full validated observation digest, provider/resource/capability, policy revision, trusted risk/risk-policy provenance, material reviewed changes/findings, semantic provenance and the exact policy/approval authorization basis.
9. Canonical authority material uses deterministic domain-separated, length-delimited hashing rather than ambiguous concatenation or debug serialization.
10. Durable states represent at least `Prepared`, `Indeterminate`, `Verified`, `Committed`, `Aborted` and `RecoveryBlocked` with a validated transition graph per generation.
11. A future executor may be callable only after the exact expected transaction/generation/binding has atomically transitioned `Prepared` → `Indeterminate` and the transition + audit write has durably committed.
12. Exactly one caller can win that pre-dispatch compare-and-swap. Only that winner may receive a process-local generation-bound dispatch permit; the permit is sealed, non-cloneable, non-serializable, non-persistable, non-reconstructible from durable state and consumed by value by any future executor API.
13. A lost permit after crash is not recreated for the same generation; `Indeterminate` remains sticky and authoritative recovery is required.
14. Authoritative evidence proving the intended effect absent permits only current-authority revalidation and an explicit append of generation N+1; it does not itself grant retry. Current observation freshness, policy and required approval must be re-established before the next prepared generation is atomically recorded.
15. Authoritative proof of intended state may advance the exact generation to `Verified`; conflicting evidence blocks automatic recovery; stale/ambiguous evidence remains indeterminate.
16. Commit is permitted only after verification and atomically records verified transaction state plus desired-state/graph/provenance content references/digests.
17. Every durable state transition, generation append and recovery decision writes an append-only audit event atomically with the transaction update.
18. Audit sequence/hash continuity, generation continuity/immutability and current-state/event consistency are verified when the store is opened or explicitly integrity-checked; internal chaining is not represented as protection against coherent rollback of the entire database.
19. Persisted transaction/audit inputs and aggregate storage have explicit resource bounds; capacity exhaustion fails closed without silent authority-history eviction.
20. Corruption, unsupported newer schema, migration mismatch and invalid durable authority state fail closed with diagnosable errors.
21. The durability claim is explicitly scoped to qualified local filesystems/storage honoring SQLite locking/sync semantics; coherent host/VM snapshot rollback and authority-database restore remain unsupported in v0.4 without an external monotonic anchor/restore protocol.

## Trust-boundary invariants

- `linura-control` remains the only workspace consumer/orchestrator of `linura-policy`.
- SQLite/persistence code cannot import policy, D-Bus, concrete Linux observation providers or privileged executors.
- A durable `Prepared` generation is evidence that the canonical `prepare` stage was reached; it is **not** an executor credential or permission to mutate Linux.
- Policy `Allow`, approval evidence, a reviewed plan, a prepare record, a transaction ID and a generation number remain distinct from execution authority.
- Prior generation bindings are immutable. Recovery may append generation N+1 only through the typed Control-owned no-effect recovery path; ordinary changed-binding request reuse remains an idempotency conflict.
- A future dispatch is forbidden while a transaction generation is merely `Prepared`; the exact generation-bound durable `Indeterminate` handoff must commit before any executor call.
- Durable `Indeterminate` state is not itself a reusable dispatch credential. Only the single caller that wins the `Prepared` → `Indeterminate` transition can receive the corresponding one-shot process-local permit, and that permit cannot be reconstructed after restart.
- `Deny`, `Blocked`, no-change, stale/mismatched authority material, stale authoritative observation, expired/revoked required approval and invalid risk binding cannot become prepared mutation authority.
- A `PlanId`, request ID, approval ID, evidence ID, transaction ID or generation number alone is insufficient authority evidence.
- Database state never replaces authoritative Linux observation for machine truth.
- Restart never means retry. An indeterminate operation requires fresh authoritative re-observation and then current authority revalidation before any future new generation/attempt.
- Audit history is append-only and integrity-checked within the retained monotonic database history; v0.4 does not claim internal detection of a complete coherent database rollback.
- v0.4 adds no executor handle, Polkit grant, generic shell authority, public `apply`/execute/mutate path or supported external effect.
- Models and agents remain proposal-only and cannot construct trusted prepare bindings, recovery evidence or dispatch permits.

## Implementation scope

- Add ADR 0019 selecting the pure transaction-domain + SQLite/WAL adapter split and defining immutable recovery generations plus the pre-dispatch durable-indeterminate/one-shot-permit handoff.
- Add `linura-transaction` for transaction identity, immutable generation identity/bindings, authority-binding digests, state/recovery semantics, one-shot pre-dispatch capability semantics and repository abstraction.
- Add `linura-persistence-sqlite` for the concrete local store, schema migrations, atomic transition/generation/audit writes and integrity validation.
- Extend the canonical observation/plan/review lineage with enough complete observation digest/freshness material for prepare-time validation; do not rely on `evidence_id` alone.
- Extend `linura-control` with durable prepare/recovery orchestration that consumes trusted retained canonical review + fresh observation material and current approval validation without exposing a mutation surface.
- Add machine-readable layering rules preventing policy/transport/provider/executor coupling into transaction/persistence crates.
- Add permanent unit/integration tests for binding substitution, observation expiry/substitution, restart idempotency, immutable generation history, recovery-generation CAS races, migration/version handling, corruption detection, append-only audit, transition legality, recovery classification, pre-dispatch one-shot handoff and resource bounds.
- Add disposable-VM qualification for process kill, abrupt guest power interruption and reopen/integrity behavior on the qualified local filesystem/SQLite runtime, without performing a Linura-managed external machine mutation.
- Add repository checks that v0.4 retains `executor_state = none`, `managed_mutation_support = none` and `complete_lifecycle = false` until the release has terminal publication evidence.

## Required acceptance evidence

- Exact-source CI, Security and CodeQL success.
- Strict workspace fmt/clippy/test and `cargo xtask check` success.
- SQLite store tests cover WAL configuration, reopen durability, schema/application version checks, migration identity, integrity checks and append-only audit enforcement.
- Restart/idempotency test proves an exact ordinary retry returns the same transaction/generation after reopening the database and a changed binding through normal prepare is rejected.
- Generation-history tests prove prior bindings remain immutable, generation numbers are contiguous, and an explicit no-effect recovery can append generation N+1 only after current observation/policy/approval revalidation.
- Recovery race tests prove two callers cannot append sibling next generations from the same `Indeterminate` predecessor.
- Observation-binding tests prove changed authority/freshness/attributes change the prepare binding and stale/expired observation cannot prepare.
- Pre-dispatch tests prove executor eligibility cannot exist while the current generation is `Prepared` and only one compare-and-swap winner can obtain a generation-bound dispatch permit after the durable `Indeterminate` transition commits; v0.4 itself invokes no executor.
- Dispatch-permit tests prove the permit is non-cloneable/non-serializable/non-persistable/non-reconstructible by API construction, is consumed at most once by the future-facing dispatch boundary contract, and cannot be recreated from an `Indeterminate` row after simulated restart.
- Recovery tests prove `Indeterminate` survives restart and cannot become retry-eligible merely from restart, duplicate delivery, a lost permit or executor self-report.
- Recovery tests prove no-effect evidence permits only reauthorization/re-prepare and an explicit next-generation append; expired/revoked approval still blocks a new generation.
- Recovery tests prove intended-state evidence advances to `Verified`, conflicting evidence becomes `RecoveryBlocked`, and stale/ambiguous evidence remains `Indeterminate`.
- Commit-before-verification and invalid/forged binding paths fail closed.
- Approval-required preparation tests prove expired/revoked/mismatched approval is rejected at prepare time.
- Corruption/future-schema/migration-checksum negative tests fail closed without rewriting the database.
- Ordinary retained-history audit mutation/deletion/tampering negative tests are rejected or detected, while the qualification explicitly does **not** claim detection of a complete coherent database rollback.
- Resource-bound tests reject oversized/over-capacity durable authority state without silent eviction.
- Disposable VM/fault evidence includes process `SIGKILL` around transaction commit boundaries, abrupt guest power interruption after acknowledged durable transition, representative write/I/O failure behavior, reopen integrity checks and WAL/checkpoint-sensitive recovery where deterministically injectable.
- Qualification records the exact filesystem/storage/hypervisor assumptions and distinguishes process restart, abrupt guest power loss and unsupported coherent host/snapshot rollback.
- Fresh exact-head Codex authority/security review returns with all valid findings resolved against the validated final head.

## Explicit non-goals

- No privileged executor implementation or qualification; that belongs to v0.5.
- No Polkit integration.
- No supported Linura-managed external machine mutation; the first supported Experimental effect remains v0.6.
- No public `apply`, execute, mutate or generic command surface.
- No claim of complete eleven-stage lifecycle integration.
- No supported distribution, desktop/headless, architecture, hardware or machine-profile boundary.
- No durable agent/model authority.
- No hosted/fleet persistence dependency.
- No full persistent intent/Setup/Profile/Library lifecycle; that remains v0.7 scope.
- No assertion that database state is authoritative current Linux state.
- No transparent authority-database restore/rollback or VM-snapshot rollback guarantee without a future independently protected monotonic epoch/anchor.
- No claim that SQLite `synchronous=FULL` alone proves arbitrary hardware/storage durability.

## Exit criteria

- [ ] Required transaction-domain and SQLite persistence capabilities are implemented.
- [ ] Exact review/approval/full-observation-to-prepare binding is revalidated and durable per immutable generation.
- [ ] Durable pre-dispatch `Indeterminate` handoff and single-use permit semantics are implemented and independently testable without an executor.
- [ ] Explicit no-effect recovery can append a fresh currently authorized generation without rebinding prior history, while normal changed-binding request reuse remains rejected.
- [ ] Restart, replay, observation-expiry/substitution, corruption, duplicate-handoff and indeterminate-recovery negative paths fail closed.
- [ ] Process-kill, abrupt guest-power and I/O-failure qualification is green within the named local storage assumptions.
- [ ] Permanent acceptance and VM evidence is green on the exact candidate source.
- [ ] All review threads are resolved against validated code and a fresh exact-head authority/security review is complete.
- [ ] Known limitations and unsupported states are documented.
- [ ] The frozen `docs/releases/v0.4.0.md` release contract is authored with PR/commit traceability.
- [ ] `CHANGELOG.md` contains the concise v0.4 version summary/link at release freeze.
- [ ] Protected proof-first/tag-last publication and independent verification complete before the machine roadmap is advanced to v0.5.

## Release handoff

The frozen v0.4.0 contract may claim an **Experimental durable reviewed-authority transaction/recovery foundation** only within its explicitly qualified local SQLite/filesystem/storage assumptions. It may claim restart-stable exact request identity, immutable per-generation prepare bindings, complete fresh authoritative-observation binding, a durable generation-bound pre-dispatch indeterminate handoff with one-shot non-reconstructible permit semantics, recovery-safe ambiguous state, verified local commit metadata and append-only integrity-checked retained audit evidence.

It must explicitly state that no v0.4 transaction, generation, prepare/indeterminate record, policy decision, approval evidence or durable database row authorizes an executor or external machine mutation; complete coherent database/snapshot rollback is not internally detectable or supported; and `synchronous=FULL` is not a universal hardware durability guarantee. v0.5 receives the durable prepared/pre-dispatch transaction contract for qualification of one narrow executor/verifier component; v0.6 remains the first milestone allowed to integrate and publish a supported managed external effect.
