# v0.4.0 — durable transaction and recovery foundation

**Status:** planned
**Target claim class:** Experimental

## Goal

Prove that Linura can carry the exact v0.3 reviewed authority subject and complete authoritative-observation binding across process restart into a durable prepare/pre-dispatch/recovery/verified-commit record **without granting execution authority or performing a managed external effect**.

v0.4 closes the authority-to-durability and pre-dispatch crash boundaries needed before privileged executor qualification can begin in v0.5.

## Required capabilities

1. A persistence-neutral durable transaction domain owns typed transaction identity, exact authority-binding material, transaction state transitions, recovery decisions and repository contracts.
2. A local SQLite/WAL adapter implements those contracts with transactional migrations, explicit application/schema versioning, migration checksum verification, `synchronous=FULL`, foreign keys and fail-closed integrity checks.
3. Durable request idempotency is namespaced by authenticated principal + request ID and survives database/process reopen within one monotonic authority-database history.
4. Same idempotency key + exact authority binding returns the existing transaction; changed binding is rejected as conflict.
5. `linura-control` revalidates the current trusted policy review, complete authoritative observation freshness/material and any required approval at prepare time and creates the durable binding from trusted canonical material.
6. The prepare binding covers principal, request, plan, full validated observation digest, provider/resource/capability, policy revision, trusted risk/risk-policy provenance, material reviewed changes/findings, semantic provenance and the exact policy/approval authorization basis.
7. Canonical authority material uses deterministic domain-separated, length-delimited hashing rather than ambiguous concatenation or debug serialization.
8. Durable states represent at least `Prepared`, `Indeterminate`, `Verified`, `Committed`, `Aborted` and `RecoveryBlocked` with a validated transition graph.
9. A future executor may be callable only after the exact current generation has durably transitioned `Prepared` → `Indeterminate`; any dispatch capability/token is created only after that transaction + audit write commits.
10. `Indeterminate` is sticky across restart unless fresh authoritative recovery evidence resolves it.
11. Authoritative evidence proving the intended effect absent permits only current-authority revalidation/re-prepare eligibility; it does not itself grant retry. Current observation freshness, policy and required approval must be re-established before a new prepared generation.
12. Authoritative proof of intended state may advance to `Verified`; conflicting evidence blocks automatic recovery; stale/ambiguous evidence remains indeterminate.
13. Commit is permitted only after verification and atomically records verified transaction state plus desired-state/graph/provenance content references/digests.
14. Every durable state transition writes an append-only audit event atomically with the transaction update.
15. Audit sequence/hash continuity and current-state/event consistency are verified when the store is opened or explicitly integrity-checked; internal chaining is not represented as protection against coherent rollback of the entire database.
16. Persisted transaction/audit inputs and aggregate storage have explicit resource bounds; capacity exhaustion fails closed without silent authority-history eviction.
17. Corruption, unsupported newer schema, migration mismatch and invalid durable authority state fail closed with diagnosable errors.
18. The durability claim is explicitly scoped to qualified local filesystems/storage honoring SQLite locking/sync semantics; coherent host/VM snapshot rollback and authority-database restore remain unsupported in v0.4 without an external monotonic anchor/restore protocol.

## Trust-boundary invariants

- `linura-control` remains the only workspace consumer/orchestrator of `linura-policy`.
- SQLite/persistence code cannot import policy, D-Bus, concrete Linux observation providers or privileged executors.
- A durable `Prepared` record is evidence that the canonical `prepare` stage was reached; it is **not** an executor credential or permission to mutate Linux.
- Policy `Allow`, approval evidence, a reviewed plan, a prepare record and a transaction ID remain distinct from execution authority.
- A future dispatch is forbidden while a transaction generation is merely `Prepared`; the generation-bound durable `Indeterminate` handoff must commit before any executor call.
- `Deny`, `Blocked`, no-change, stale/mismatched authority material, stale authoritative observation, expired/revoked required approval and invalid risk binding cannot become prepared mutation authority.
- A `PlanId`, request ID, approval ID, evidence ID or transaction ID alone is insufficient authority evidence.
- Database state never replaces authoritative Linux observation for machine truth.
- Restart never means retry. An indeterminate operation requires fresh authoritative re-observation and then current authority revalidation before any future new attempt.
- Audit history is append-only and integrity-checked within the retained monotonic database history; v0.4 does not claim internal detection of a complete coherent database rollback.
- v0.4 adds no executor handle, Polkit grant, generic shell authority, public `apply`/execute/mutate path or supported external effect.
- Models and agents remain proposal-only and cannot construct trusted prepare bindings or recovery evidence.

## Implementation scope

- Add ADR 0019 selecting the pure transaction-domain + SQLite/WAL adapter split and defining the pre-dispatch durable-indeterminate handoff.
- Add `linura-transaction` for transaction identity, authority-binding digests, state/recovery semantics and repository abstraction.
- Add `linura-persistence-sqlite` for the concrete local store, schema migrations, atomic transition/audit writes and integrity validation.
- Extend the canonical observation/plan/review lineage with enough complete observation digest/freshness material for prepare-time validation; do not rely on `evidence_id` alone.
- Extend `linura-control` with durable prepare orchestration that consumes trusted retained canonical review + fresh observation material and current approval validation without exposing a mutation surface.
- Add machine-readable layering rules preventing policy/transport/provider/executor coupling into transaction/persistence crates.
- Add permanent unit/integration tests for binding substitution, observation expiry/substitution, restart idempotency, migration/version handling, corruption detection, append-only audit, transition legality, recovery classification, pre-dispatch handoff and resource bounds.
- Add disposable-VM qualification for process kill, abrupt guest power interruption and reopen/integrity behavior on the qualified local filesystem/SQLite runtime, without performing a Linura-managed external machine mutation.
- Add repository checks that v0.4 retains `executor_state = none`, `managed_mutation_support = none` and `complete_lifecycle = false` until the release has terminal publication evidence.

## Required acceptance evidence

- Exact-source CI, Security and CodeQL success.
- Strict workspace fmt/clippy/test and `cargo xtask check` success.
- SQLite store tests cover WAL configuration, reopen durability, schema/application version checks, migration identity, integrity checks and append-only audit enforcement.
- Restart/idempotency test proves an exact retry returns the same transaction after reopening the database and a changed binding is rejected.
- Observation-binding tests prove changed authority/freshness/attributes change the prepare binding and stale/expired observation cannot prepare.
- Pre-dispatch tests prove executor eligibility cannot exist while the current generation is `Prepared` and becomes representable only after the durable `Indeterminate` transition commits; v0.4 itself invokes no executor.
- Recovery tests prove `Indeterminate` survives restart and cannot become retry-eligible merely from restart or duplicate delivery.
- Recovery tests prove no-effect evidence permits only reauthorization/re-prepare; expired/revoked approval still blocks a new generation.
- Recovery tests prove intended-state evidence advances to `Verified`, conflicting evidence becomes `RecoveryBlocked`, and stale/ambiguous evidence remains `Indeterminate`.
- Commit-before-verification and invalid/forged binding paths fail closed.
- Approval-required preparation tests prove expired/revoked/mismatched approval is rejected at prepare time.
- Corruption/future-schema/migration-checksum negative tests fail closed without rewriting the database.
- Ordinary retained-history audit mutation/deletion/tampering negative tests are rejected or detected, while the qualification explicitly does **not** claim detection of a complete coherent database rollback.
- Resource-bound tests reject oversized/over-capacity durable authority state without silent eviction.
- Disposable VM/fault evidence includes process `SIGKILL` around transaction commit boundaries, abrupt guest power interruption after acknowledged durable transition, representative write/I/O failure behavior, reopen integrity checks and WAL/checkpoint-sensitive recovery where deterministically injectable.
- Qualification records the exact filesystem/storage/hypervisor assumptions and distinguishes process restart, abrupt guest power loss and unsupported coherent host/snapshot rollback.
- Fresh exact-head Codex authority/security review returns with all valid findings resolved against the validated final head.

## Explicit non-goals

- No privileged executor implementation or qualification; that belongs to v0.5.
- No Polkit integration.
- No supported Linura-managed external machine mutation; the first supported Experimental effect remains v0.6.
- No public `apply`, execute, mutate or generic command surface.
- No claim of complete eleven-stage lifecycle integration.
- No supported distribution, desktop/headless, architecture, hardware or machine-profile boundary.
- No durable agent/model authority.
- No hosted/fleet persistence dependency.
- No full persistent intent/Setup/Profile/Library lifecycle; that remains v0.7 scope.
- No assertion that database state is authoritative current Linux state.
- No transparent authority-database restore/rollback or VM-snapshot rollback guarantee without a future independently protected monotonic epoch/anchor.
- No claim that SQLite `synchronous=FULL` alone proves arbitrary hardware/storage durability.

## Release handoff

The frozen v0.4.0 contract may claim an **Experimental durable reviewed-authority transaction/recovery foundation** only within its explicitly qualified local SQLite/filesystem/storage assumptions. It may claim restart-stable exact prepare identity, complete fresh authoritative-observation binding, a durable generation-bound pre-dispatch indeterminate handoff, recovery-safe ambiguous state, verified local commit metadata and append-only integrity-checked retained audit evidence.

It must explicitly state that no v0.4 transaction, prepare/indeterminate record, policy decision or approval evidence authorizes an executor or external machine mutation; complete coherent database/snapshot rollback is not internally detectable or supported; and `synchronous=FULL` is not a universal hardware durability guarantee. v0.5 receives the durable prepared/pre-dispatch transaction contract for qualification of one narrow executor/verifier component; v0.6 remains the first milestone allowed to integrate and publish a supported managed external effect.
