# v0.4.0 — durable transaction and recovery foundation

**Status:** planned
**Target claim class:** Experimental

## Goal

Prove that Linura can carry the exact v0.3 reviewed authority subject across process restart into a crash-safe, corruption-detecting durable prepare/recovery/verified-commit record **without granting execution authority or performing a managed external effect**.

v0.4 closes the authority-to-durability boundary needed before privileged executor qualification can begin in v0.5.

## Required capabilities

1. A persistence-neutral durable transaction domain owns typed transaction identity, exact authority-binding material, transaction state transitions, recovery decisions and repository contracts.
2. A local SQLite/WAL adapter implements those contracts with transactional migrations, explicit application/schema versioning, migration checksum verification, `synchronous=FULL`, foreign keys and fail-closed integrity checks.
3. Durable request idempotency is namespaced by authenticated principal + request ID and survives database/process reopen.
4. Same idempotency key + exact authority binding returns the existing transaction; changed binding is rejected as conflict.
5. `linura-control` revalidates the current trusted policy review and any required approval at prepare time and creates the durable binding from trusted canonical material.
6. The prepare binding covers principal, request, plan, authoritative evidence, provider/resource/capability, policy revision, trusted risk/risk-policy provenance, material reviewed changes/findings, semantic provenance and the exact policy/approval authorization basis.
7. Canonical authority material uses deterministic domain-separated, length-delimited hashing rather than ambiguous concatenation or debug serialization.
8. Durable states represent at least `Prepared`, `Indeterminate`, `Verified`, `Committed`, `Aborted` and `RecoveryBlocked` with a validated transition graph.
9. `Indeterminate` is sticky across restart unless fresh authoritative recovery evidence resolves it.
10. Only authoritative evidence proving the intended effect absent may reopen a new prepared attempt; authoritative proof of intended state may advance to `Verified`; conflicting evidence blocks automatic recovery; stale/ambiguous evidence remains indeterminate.
11. Commit is permitted only after verification and atomically records verified transaction state plus desired-state/graph/provenance content references/digests.
12. Every durable state transition writes an append-only audit event atomically with the transaction update.
13. Audit sequence/hash continuity and current-state/event consistency are verified when the store is opened or explicitly integrity-checked.
14. Persisted transaction/audit inputs and aggregate storage have explicit resource bounds; capacity exhaustion fails closed without silent authority-history eviction.
15. Corruption, unsupported newer schema, migration mismatch and invalid durable authority state fail closed with diagnosable errors.

## Trust-boundary invariants

- `linura-control` remains the only workspace consumer/orchestrator of `linura-policy`.
- SQLite/persistence code cannot import policy, D-Bus, concrete Linux observation providers or privileged executors.
- A durable `Prepared` record is evidence that the canonical `prepare` stage was reached; it is **not** an executor credential or permission to mutate Linux.
- Policy `Allow`, approval evidence, a reviewed plan, a prepare record and a transaction ID remain distinct from execution authority.
- `Deny`, `Blocked`, no-change, stale/mismatched authority material, expired/revoked required approval and invalid risk binding cannot become prepared mutation authority.
- A `PlanId`, request ID, approval ID or transaction ID alone is insufficient authority evidence.
- Database state never replaces authoritative Linux observation for machine truth.
- Restart never means retry. An indeterminate operation requires fresh authoritative re-observation before any future effect could be retried.
- Audit history is append-only and integrity-checked; corruption is not repaired by silently rewriting authority history.
- v0.4 adds no executor handle, Polkit grant, generic shell authority, public `apply`/execute/mutate path or supported external effect.
- Models and agents remain proposal-only and cannot construct trusted prepare bindings or recovery evidence.

## Implementation scope

- Add ADR 0019 selecting the pure transaction-domain + SQLite/WAL adapter split.
- Add `linura-transaction` for transaction identity, authority-binding digests, state/recovery semantics and repository abstraction.
- Add `linura-persistence-sqlite` for the concrete local store, schema migrations, atomic transition/audit writes and integrity validation.
- Extend `linura-control` with durable prepare orchestration that consumes trusted retained canonical review material and current approval validation without exposing a mutation surface.
- Add machine-readable layering rules preventing policy/transport/provider/executor coupling into transaction/persistence crates.
- Add permanent unit/integration tests for binding substitution, restart idempotency, migration/version handling, corruption detection, append-only audit, transition legality, recovery classification and resource bounds.
- Add disposable-VM qualification that proves persistence/reopen and no-blind-replay semantics on an actual Linux filesystem/SQLite runtime without performing a managed machine mutation.
- Add repository checks that v0.4 retains `executor_state = none`, `managed_mutation_support = none` and `complete_lifecycle = false` until the release has terminal publication evidence.

## Required acceptance evidence

- Exact-source CI, Security and CodeQL success.
- Strict workspace fmt/clippy/test and `cargo xtask check` success.
- SQLite store tests cover WAL configuration, reopen durability, schema/application version checks, migration identity, integrity checks and append-only audit enforcement.
- Restart/idempotency test proves an exact retry returns the same transaction after reopening the database and a changed binding is rejected.
- Recovery tests prove `Indeterminate` survives restart and cannot become retry-eligible without fresh authoritative evidence proving the effect absent.
- Recovery tests prove intended-state evidence advances to `Verified`, conflicting evidence becomes `RecoveryBlocked`, and stale/ambiguous evidence remains `Indeterminate`.
- Commit-before-verification and invalid/forged binding paths fail closed.
- Approval-required preparation tests prove expired/revoked/mismatched approval is rejected at prepare time.
- Corruption/future-schema/migration-checksum negative tests fail closed without rewriting the database.
- Audit mutation/deletion/tampering negative tests are rejected or detected.
- Resource-bound tests reject oversized/over-capacity durable authority state without silent eviction.
- Disposable VM evidence demonstrates persistent state survives daemon/process restart and ambiguous recovery does not blindly replay an effect.
- Fresh exact-head Codex authority/security review returns with all valid findings resolved against the validated final head.

## Explicit non-goals

- No privileged executor implementation or qualification; that belongs to v0.5.
- No Polkit integration.
- No supported Linura-managed external machine mutation; the first supported Experimental effect remains v0.6.
- No public `apply`, execute, mutate or generic command surface.
- No claim of complete eleven-stage lifecycle integration.
- No supported distribution, desktop/headless, architecture, hardware or machine-profile boundary.
- No durable agent/model authority.
- No hosted/fleet persistence dependency.
- No full persistent intent/Setup/Profile/Library lifecycle; that remains v0.7 scope.
- No assertion that database state is authoritative current Linux state.

## Exit criteria

- [ ] Required transaction-domain and SQLite persistence capabilities are implemented.
- [ ] Exact review/approval-to-prepare binding is revalidated and durable.
- [ ] Restart, replay, corruption and indeterminate-recovery negative paths fail closed.
- [ ] Permanent acceptance and VM evidence is green on the exact candidate source.
- [ ] All review threads are resolved against validated code and a fresh exact-head authority/security review is complete.
- [ ] Known limitations and unsupported states are documented.
- [ ] The frozen `docs/releases/v0.4.0.md` release contract is authored with PR/commit traceability.
- [ ] `CHANGELOG.md` contains the concise v0.4 version summary/link at release freeze.
- [ ] Protected proof-first/tag-last publication and independent verification complete before the machine roadmap is advanced to v0.5.

## Release handoff

The frozen v0.4.0 contract may claim an **Experimental durable reviewed-authority transaction/recovery foundation** only. It may claim restart-stable exact prepare identity, recovery-safe indeterminate state, verified local commit metadata and append-only integrity-checked audit evidence within the qualified local SQLite boundary.

It must explicitly state that no v0.4 transaction, prepare record, policy decision or approval evidence authorizes an executor or external machine mutation. v0.5 receives the durable prepared-transaction contract for qualification of one narrow executor/verifier component; v0.6 remains the first milestone allowed to integrate and publish a supported managed external effect.
