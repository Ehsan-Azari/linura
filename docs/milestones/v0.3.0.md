# v0.3.0 — policy, authorization, approval, and plan review

**Status:** planned  
**Target claim class:** Experimental

## Goal

Complete Linura's authority-side **plan review** boundary on top of the v0.2 canonical deterministic reconciliation plan without introducing supported external mutation.

The target path is:

```text
authenticated semantic request
→ authoritative observation
→ deterministic ReconciliationPlan
→ structural validation
→ authenticated policy-review subject
→ deterministic policy evaluation
→ approval requirement / approval evidence when required
→ reviewed-plan result
```

The milestone stops before durable prepare, execution, post-effect verification, commit, mutation audit and reconciliation. A reviewed or approved plan remains non-executable at the public product boundary.

## Canonical plan lineage

v0.3 extends the v0.2 `linura-planner::ReconciliationPlan` lineage. It must not revive or create a competing provider-owned/executable planning model.

The superseded bootstrap path `ActionRequest → Provider::plan → ActionPlan → ControlPlane::apply` is not part of this milestone. Policy receives a review projection created by Linura from the canonical reconciliation plan plus authenticated principal identity. Clients, providers and models cannot author that projection independently.

## Required capabilities

1. `linura-policy` consumes a canonical review subject derived from `ReconciliationPlan`, not provider-generated effects or transport data.
2. Policy outcomes are deterministic and typed: `allow`, `deny`, `require-approval`, or `blocked`.
3. Blocked/invalid plans cannot be promoted into approval merely because a caller asks for review.
4. Review binds the authenticated principal to the exact request, plan, authoritative evidence identity, provider, resource, capability and policy snapshot/revision.
5. Policy and approval explanations preserve semantic reason/provenance and the material planned changes being reviewed.
6. Approval requirements define the required approval class and explicit approver constraints; unsupported/unknown requirements fail closed.
7. Approval evidence is authenticated and bound to the exact review binding. A changed plan, evidence identity, principal, policy revision, resource or capability invalidates reuse.
8. Approval evidence has explicit issuance/expiry semantics and can be revoked. Expired or revoked evidence cannot satisfy a current review.
9. An agent/model cannot approve its own proposal, mint approval evidence, change its authenticated principal, or bypass required human/admin policy.
10. Review lookup/retry semantics are deterministic and bounded. Any v0.3 retention may remain process-local; it must not be described as durable authorization state.
11. Public reviewed-plan output remains explicitly non-executable. No executor handle, Polkit grant, prepare record or `apply` conversion is exposed.
12. D-Bus/CLI/SDK surfaces remain adapters to transport-neutral authority semantics rather than owning policy or approval rules.

## Exact review binding

At minimum, every policy evaluation and approval check is correlated with:

```text
authenticated principal
request id
plan id
canonical planned changes/findings
observed evidence id
provider + resource + capability
semantic provenance
prospective risk
policy id + policy revision
approval requirement/evidence when applicable
```

`PlanId` alone is not sufficient authority evidence. In particular, v0.2 currently derives the plan ID from the request identity; therefore v0.3 must also bind current evidence and policy identity, and must reject any review whose material plan content no longer matches the reviewed subject.

## Determinism contract

For identical normalized review inputs — authenticated principal, canonical reconciliation plan, authoritative evidence identity and policy snapshot — policy evaluation and the reviewed-plan result must be identical.

Wall-clock time may participate only through explicit bounded approval issuance/expiry checks. It must not alter the underlying deterministic policy decision for the same policy snapshot and review subject.

## Trust-boundary invariants

- The authenticated principal is derived by the trusted local transport/control boundary; it is not supplied by the client payload.
- `Actor` remains provenance about who/what requested the work; it is not a substitute for authenticated principal identity.
- Models are untrusted proposers and never become policy or approval authorities.
- Policy evaluation does not call providers, executors, Polkit, shells or model providers.
- Approval does not create execution authority.
- `allow` does not create execution authority.
- A reviewed plan does not create a durable prepare record.
- Unknown policy, unknown approval class, missing evidence, stale review binding, expired approval and revoked approval fail closed.
- Review never upgrades cached/retrieved context into authoritative observation.
- The canonical eleven-stage lifecycle is unchanged; v0.3 proves only the `authorize`-side review boundary and deliberately stops before `prepare`.

## Core acceptance cases

The deterministic core must prove at minimum:

1. a valid low-risk subject can return `allow`;
2. policy can return explicit `deny`;
3. system mutation can require interactive approval;
4. security-sensitive work can require administrator approval;
5. destructive work can require a dedicated destructive approval class;
6. a blocked plan returns `blocked` and cannot be approved;
7. an agent cannot self-authorize a mutation;
8. review binds the authenticated principal;
9. review binds the exact plan/request and authoritative evidence identity;
10. a different policy revision cannot reuse a prior evaluation/approval;
11. a different provider/resource/capability cannot reuse prior approval;
12. expired approval is rejected;
13. revoked approval is rejected;
14. an unauthorized approver is rejected;
15. deterministic retry returns the same review result for the same normalized input;
16. an approved reviewed plan still reports no execution authority and performs no native Linux mutation.

## Persistence and recovery boundary

v0.3 may use bounded process-local review/approval retention to prove semantics, but it does not claim durable authorization state across daemon restart. Durable request/plan/review binding, prepare state, replay prevention across restart, corruption handling and indeterminate recovery belong to v0.4.

If process-local review evidence is lost, the caller must obtain a fresh authoritative observation, plan and review rather than reconstruct authority from stale client state.

## Compatibility boundary

All v0.3 contracts remain Experimental. They may evolve coherently while Linura is pre-1.0, subject to `contracts/stability.toml` and the repository's contract-change procedure.

Removing the unused bootstrap `ActionPlan`/`ActionRequest`/`PlanResponse`/generic `Provider::plan`/`MutationRuntime` scaffolding is an intentional Experimental contract cleanup: those types are not preserved as a legacy compatibility path because they conflict with the canonical v0.2 plan lineage and have no supported user capability.

## Explicit non-goals

v0.3 does **not** claim:

- durable approval or transaction persistence;
- a prepared mutation or intent-to-execute record;
- executable effect generation as a public product contract;
- Polkit authorization or privileged credential acquisition;
- any public `apply`, execute or mutate method;
- privileged executor integration;
- post-mutation verification;
- commit/audit/reconciliation of a real effect;
- complete eleven-stage managed mutation;
- natural-language/model interpretation;
- fleet/remote authority;
- a supported Linux distribution, desktop, machine class, hardware profile or virtualization profile;
- production readiness.

## Publication exit criteria

Before v0.3.0 can be released:

- the exact release source passes canonical CI, Security and CodeQL with no unresolved blocking review threads;
- `docs/qualification/v0.3.0.md` maps every bounded claim to reproducible positive/negative/failure evidence;
- deterministic policy/approval tests cover allow, deny, require-approval, blocked and binding-mismatch cases;
- hostile-input/resource bounds are defined for every new public review/approval surface;
- the threat model covers approval replay/theft, stale-plan approval, policy substitution, self-approval, approver escalation and confused-deputy cases;
- exact-source VM acceptance proves the existing v0.2 observation/planning behavior remains intact and proves that policy review/approval does not mutate native Linux state;
- every public reviewed-plan representation remains explicitly non-executable;
- no v0.4+ durable prepare, v0.5 executor qualification or v0.6 supported mutation claim is pulled forward into this milestone;
- normal Trusted Release Proof, immutable tag-last publication and independent release verification complete for the exact selected source.
