# v0.2.0 — deterministic desired state and non-executable planning

**Status:** implementation in progress  
**Target claim class:** Experimental

## Goal

Prove that Linura can turn a hand-authored, authenticated semantic request into normalized desired state and compare that desired state with current authoritative machine evidence to produce a deterministic, explainable **plan preview** without acquiring or exercising mutation authority.

The target pipeline is:

```text
hand-authored intent
→ requirements
→ capability resolution
→ conflict detection
→ normalized desired state
→ current authoritative observation
→ deterministic diff
→ structural validation
→ non-executable plan preview
```

`v0.2.0` deliberately stops before authorization, prepare, execution, post-mutation verification, commit, audit and reconciliation.

## Required capabilities

1. Typed capability blueprints contribute provider-neutral declarative resource state rather than command strings.
2. Capability resolution is deterministic and fails closed on missing capabilities or declared conflicts.
3. Multiple capability contributions to the same resource are merged deterministically; contradictory values for the same desired attribute are rejected.
4. Desired resources bind the resource identity, authoritative observation provider/capability route, normalized state attributes and semantic origin.
5. Every desired resource retains an intent, requirement or capability origin; anonymous managed state is invalid.
6. Planning requires a current authoritative observation whose provider/resource/capability identity matches the desired-state route.
7. The planner emits deterministic state differences and distinguishes `no-change`, `change-proposed` and `blocked` results.
8. A desired attribute absent from authoritative evidence produces a blocker instead of an inferred or guessed current value.
9. Every preview carries the exact evidence identity used to derive the diff.
10. Every preview explicitly reports `execution_authorized = false`.
11. A bounded process-local plan store preserves request/plan-id idempotency during the daemon lifetime and rejects reuse of the same identifier for a different preview.
12. Experimental JSON contracts define capability resource blueprints, desired state and non-executable plan previews.

## Determinism contract

For identical normalized inputs—actor, request ID, intent and requirements, capability catalog, desired state and authoritative observation projection—the planner must produce the same ordered desired-state representation, changes, findings, status and plan identity.

Determinism is achieved with typed identifiers and ordered collections at the domain boundary. Hash-map iteration order, wall-clock sampling, model output, shell discovery and executor behavior are not planning inputs.

The authoritative evidence identifier is part of the input identity. A new observation can therefore legitimately produce a different preview even when the semantic request is unchanged.

## Trust-boundary invariants

- The planner is a pure domain component and does not depend on D-Bus transport representations.
- A model provider is not required and cannot inject executable effects through this milestone.
- Capability blueprints describe desired state and observation routes, not shell commands.
- Planning never calls an executor.
- Planning never invokes Polkit or obtains privileged authorization.
- A proposed system change may be classified prospectively as mutation risk, but risk classification does not grant authority.
- `execution_authorized` is always false in the v0.2.0 preview contract.
- Stale or future evidence cannot be used as current state for planning.
- Unknown desired attributes fail closed.
- Conflicting desired-state contributions fail closed.

## Core acceptance cases

The deterministic core must prove at minimum:

1. identical intent/capability inputs compile to identical desired state;
2. semantic origins survive compilation;
3. missing capability resolution fails;
4. capability conflicts fail;
5. contradictory desired-state contributions fail;
6. inactive authoritative state versus desired active state yields `change-proposed`;
7. already-satisfied state yields `no-change`;
8. an unobserved desired attribute yields `blocked`;
9. stale evidence is rejected;
10. a preview requiring change remains explicitly non-executable;
11. same request/plan ID + same preview is idempotent;
12. same request/plan ID + different preview is rejected.

The later Control1/CLI integration increment must additionally prove these properties against real exact-source Linux observation in the disposable VM and prove that generating/validating/explaining a preview does not change machine state.

## Persistence and idempotency boundary

The initial plan store is intentionally bounded and process-local. It provides daemon-lifetime idempotency semantics and a safe basis for public preview lookup, but it is **not durable state** and does not survive restart.

Durable prepare/commit records, crash recovery, replay prevention across restarts and persistent audit remain later milestones. Documentation and APIs must not describe v0.2.0 process-local plan retention as durable transaction semantics.

## Compatibility boundary

The v0.2.0 planning contracts remain Experimental. They may evolve coherently while Linura is pre-1.0, subject to the repository contract-stability rules.

This milestone does not reintroduce removed pre-stable Control1 mutation or compatibility methods. Public transport additions, when implemented, use explicit plan-preview names and remain non-executable.

## Explicit non-goals

`v0.2.0` does **not** claim:

- natural-language/model interpretation;
- executor selection or executable effect generation;
- `apply` or any other public mutation method;
- policy approval authority;
- Polkit authorization;
- durable prepare/commit;
- persistent plan, intent or desired-state storage;
- post-mutation verification;
- mutation audit/reconciliation;
- compensation or rollback execution;
- complete eleven-stage managed mutation;
- supported Linux distribution, desktop, hardware or platform profile;
- First Boot;
- production readiness.

## Publication exit criteria

Before publication, the mutable milestone must close into a frozen `docs/releases/v0.2.0.md` contract. Publication requires the normal protected release lifecycle plus version-specific evidence proving the non-executable planning boundary, including exact-source disposable-VM acceptance and independent release verification.
