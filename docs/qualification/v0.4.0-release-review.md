## Review model

The release gate requires a fresh, documented adversarial review of the exact candidate source covering correctness, authority boundaries, persistence integrity, durability, recoverability, concurrency, bounded persisted input, release control and accidental execution authority. The requirement is substantive and exact-source based; it is not tied to Codex or any other review vendor. A valid finding changes the candidate and requires correction, permanent regression coverage where applicable, requalification of the new exact head, and closure of the corresponding review thread only after the evidence is green.

- workspace version `0.4.0` and coherent local-package lockfile versions;
- `CHANGELOG.md` v0.4.0 entry;
- README publication-pending status;
- v0.4 milestone publication-pending state and tool-neutral exact-head review requirement;
- `docs/qualification/v0.4.0.md`;
- this review record;
- frozen `docs/releases/v0.4.0.md`;
- release automation that reruns both v0.4 durability and genuine ext4 ENOSPC qualification before build/promotion.

The machine roadmap must remain at `current_release = "v0.3.0"` and `next_release = "v0.4.0"` until immutable publication and independent Release Verification succeed. Release preparation preserves `executor_state = "none"`, `managed_mutation_support = "none"`, `complete_lifecycle = false` and the Experimental claim class.

## Exact-head merge gate

The release-preparation PR is mergeable only when its exact final head has all of the following terminally satisfied:

- workspace version/lockfile/release-contract coherence;
- canonical CI;
- Security;
- CodeQL;
- Disposable VM acceptance;
- Control1 plan-preview VM acceptance;
- v0.4 real ext4 ENOSPC recovery qualification;
- v0.4 SQLite/WAL durability fault qualification;
- no unresolved blocking review threads;
- fresh documented exact-head adversarial authority/security/durability/release review with no actionable finding.

## Release authorization contract

Merging release preparation does not authorize publication. The later protected-main release authorization must be a metadata-only commit with exactly one parent: the reviewed release-preparation source. Its Git tree must be identical to the parent's tree, and its commit message must contain exactly one matching pair of trailers:

```text
Reviewed-Source: <immediate-parent-sha>
Reviewed-Tree: <identical-parent-and-source-tree-sha>
```

`python3 tools/release_contract.py validate-intent --source-sha <authorization-sha>` must validate that identity before proof dispatch and again inside Trusted Release Proof. No tracked file is modified to encode the reviewed tree, avoiding a self-referential tree hash.

## Protected publication gate

The tree-identical release-authorization source must receive fresh protected-main CI, Security and CodeQL. Trusted Release Proof then independently reruns authoritative-observation VM qualification, Control1 plan-preview VM qualification, v0.4 SQLite/WAL durability fault qualification and genuine loop-mounted ext4 ENOSPC recovery qualification before any release build can start. Only after all qualification succeeds may the isolated reproducible build run and promotion consume its sealed bytes without rebuilding. Publication is tag-last, and independent Release Verification must succeed from a fresh runner.

## Post-publication closure

Only after independent verification may a normal protected PR:

- advance `current_release` to `v0.4.0` and `next_release` to `v0.5.0`;
- mark the v0.4 milestone released and add final release/qualification pointers;
- update README from publication-pending to released;
- record exact release-intent, protected-main checks, Trusted Release Proof, promotion, immutable publication and Release Verification evidence;
- remove obsolete temporary v0.4 branches and closed qualification artifacts that are not required as durable evidence.

The post-publication closure must not alter the immutable v0.4 release contract/tag/assets or expand the no-executor/no-supported-external-mutation claim boundary.
