## Release-refresh source

The original release-preparation PR already froze workspace version `0.4.0`, the coherent lockfile, CHANGELOG/README publication-pending status, v0.4 milestone state, release automation and the frozen release contract. After PR #62 changed the qualified implementation tree, this refresh is intentionally limited to the human-auditable qualification/release records needed to bind publication to the final implementation lineage.

The refresh must not:

- change product/runtime code;
- change workspace/package versions;
- advance the machine roadmap before independent verification;
- change `executor_state = "none"`, `managed_mutation_support = "none"` or `complete_lifecycle = false`;
- expand the Experimental claim into production readiness or supported external mutation.

`contracts/roadmap.toml` remains `current_release = "v0.3.0"` and `next_release = "v0.4.0"` until immutable publication and independent Release Verification succeed.

## Exact-head merge gate

The release-refresh PR may merge only when its exact final head has:

- canonical CI success;
- Security success;
- CodeQL success;
- all repository-triggered exact-source qualification applicable to that head terminally green;
- no unresolved blocking review thread;
- a fresh documented adversarial release/authority/security/durability review with no actionable finding.

The later Trusted Release Proof remains responsible for rerunning the complete mandatory v0.4 qualification set on the fresh protected release authorization, including authoritative-observation VM, Control1 plan-preview VM, genuine ext4 ENOSPC recovery and SQLite/WAL durability faults.

## Release authorization contract

Merging this refresh does **not** authorize publication. The next protected-main release authorization must be a metadata-only commit with exactly one parent: the reviewed release-refresh source. Its Git tree must be identical to the parent's tree, and its commit message must contain exactly one matching pair of trailers:

```text
Reviewed-Source: <immediate-parent-sha>
Reviewed-Tree: <identical-parent-and-source-tree-sha>
```

The command

```bash
python3 tools/release_contract.py validate-intent --source-sha <authorization-sha>
```

must validate that identity before proof dispatch and again inside Trusted Release Proof. No tracked file is modified merely to encode the reviewed tree, avoiding self-referential release evidence.

## Protected publication gate

The new tree-identical release-authorization source must receive fresh protected-main checks. Trusted Release Proof then independently reruns authoritative-observation VM qualification, Control1 plan-preview VM qualification, v0.4 SQLite/WAL durability-fault qualification and genuine ext4 ENOSPC recovery before any release build may start.

Only after mandatory qualification succeeds may the isolated exact-source build run, independent reproduction verify the payload, and promotion consume the sealed proven bytes without rebuilding. Publication remains proof-first/tag-last. Independent Release Verification must then re-download and validate the published release from a fresh runner.

## Post-publication closure

Only after independent verification may a normal protected PR:

- advance `current_release` to `v0.4.0` and `next_release` to `v0.5.0`;
- mark the v0.4 milestone released and add terminal proof/publication/verification pointers;
- update README from publication-pending to released;
- record exact release authorization, protected-main checks, Trusted Release Proof, promotion, immutable publication and Release Verification evidence;
- remove obsolete temporary v0.4 working branches that are not required as durable evidence.

Post-publication closure must not alter the immutable v0.4 tag/assets/release contract or expand the no-executor/no-supported-external-mutation boundary.
