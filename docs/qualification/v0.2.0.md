# v0.2.0 qualification dossier

**Release:** `v0.2.0`
**Claim class:** Experimental
**Qualification subject:** deterministic desired state and authenticated non-executable plan previews
**Decision state:** implementation qualification satisfied; final release qualification and publication evidence remain gated by the protected release lifecycle

## Purpose

This dossier is the human-auditable claim-to-evidence map for Linura v0.2.0. It explains what the frozen release contract requires and which repository tests, exact-source VM scenarios, release-proof stages, and publication checks establish each claim.

Machine-generated CI, VM evidence, release evidence, provenance attestations, and independent publication verification remain authoritative for a particular candidate. Prose in this dossier cannot waive a failed, cancelled, skipped-when-mandatory, or missing gate.

## Qualification model

v0.2.0 uses five evidence layers:

1. **Static deterministic verification** — formatting, strict clippy/workspace tests, typed desired-state/planner tests, contract/tooling checks, historical contract validation, and non-mutating source checks.
2. **Security analysis** — dependency audit and CodeQL on the exact candidate source.
3. **System acceptance** — exact-source `linurad`/`linuractl` in a disposable Linux VM for both the authoritative-observation regression and Control1 plan-preview behavior/non-mutation.
4. **Release reproducibility and provenance** — Trusted Release Proof, both mandatory VM scenarios, isolated build, independent binary reproduction, checksums, SPDX SBOM, exact source/version identity, and attestations.
5. **Publication verification** — tag-last immutable publication followed by independent re-download and verification of public metadata, notes, evidence, candidate assets, checksums, and attestations.

All mandatory layers must succeed for the final selected release source.

## Controlled VM environment

Both mandatory system scenarios use the repository-owned disposable-VM harness:

- Ubuntu 24.04 LTS amd64 dated cloud image from the repository-pinned release URL;
- SHA-256 verification before guest creation;
- exact-source release-mode build of the required clients/services under the locked Rust toolchain;
- ephemeral cloud-init/SSH credentials;
- QEMU snapshot mode;
- deterministic hosted-runner TCG baseline, with acceleration identity recorded in evidence;
- machine-readable `VM-ACCEPTANCE-EVIDENCE.json` plus diagnostics.

This qualification environment is evidence infrastructure, not a supported Linura distribution/hardware profile.

## Mandatory deterministic-core scenarios

### Q-PLAN-001 — deterministic desired-state compilation

**Goal:** prove identical hand-authored intent/requirements/capability inputs normalize identically.

**Pass:** desired resources, ordered attributes, semantic origins, and observation routes are identical across repeated compilation.

### Q-PLAN-002 — missing capability fails closed

**Goal:** prevent implicit provider or feature fabrication.

**Pass:** capability resolution fails when a required capability cannot be resolved.

### Q-PLAN-003 — capability conflict fails closed

**Goal:** prevent incompatible declared capabilities from being silently composed.

**Pass:** conflict resolution emits deterministic failure rather than choosing one side implicitly.

### Q-PLAN-004 — contradictory desired values fail closed

**Goal:** prevent multiple contributions from assigning incompatible desired values to the same resource attribute.

**Pass:** compilation rejects the contradiction before planning.

### Q-PLAN-005 — semantic origin is mandatory

**Goal:** ensure managed desired state is attributable.

**Pass:** a desired resource with no intent/requirement/capability origin is invalid; valid origins survive into the preview.

### Q-PLAN-006 — evidence identity/freshness validation

**Goal:** ensure assumed, stale, future, or mismatched state cannot drive a current preview.

**Pass:** provider/resource/capability mismatch or non-current evidence fails before a valid preview is produced.

### Q-PLAN-007 — deterministic diff statuses

**Goal:** distinguish satisfied, proposed-change, and fail-closed states.

**Pass:** already-satisfied input yields `no-change`; differing observed state yields `change-proposed`; unavailable current attribute yields `blocked`.

### Q-PLAN-008 — non-executable authority state

**Goal:** make preview authority explicit and unforgeable.

**Pass:** every conforming preview reports `execution_authorized=false`; inconsistent wire input claiming true is rejected.

## Mandatory Control1 plan-preview VM scenarios

The repository `control1-plan-preview` scenario must exercise externally observable behavior against a controlled systemd fixture.

### Q-VM-PLAN-001 — change-proposed from native evidence

Create a known inactive fixture outside Linura, observe it through the authenticated Control1 path, request desired `active_state=active`, and receive `change-proposed` with prospective system-mutation risk and `execution_authorized=false`.

### Q-VM-PLAN-002 — exact retry replay before observation

Repeat the identical authenticated request ID/input after the first response. The response must be the exact retained preview and evidence ID. The retry must not create a new authoritative observation first.

### Q-VM-PLAN-003 — retained lookup/explanation

Retrieve and explain the retained preview by typed plan ID. The returned semantic origin, evidence identity, ordered changes/findings, status, and authority state must correspond to the retained plan without re-execution or mutation.

### Q-VM-PLAN-004 — planning is non-mutating

After preview generation/retry/lookup/explanation, re-observe through Linura and inspect native `systemctl` state. The fixture must still be inactive.

### Q-VM-PLAN-005 — no-change

Request desired state equal to current authoritative state and receive `no-change` with no execution authority.

### Q-VM-PLAN-006 — unknown current attribute blocks

Request a desired attribute not present in authoritative observation and receive a fail-closed `blocked` preview rather than a guessed current value.

### Q-VM-PLAN-007 — conflicting idempotency input

Reuse a retained request ID with materially different normalized desired input. The request must fail before re-observation and must not replace the retained preview.

## Mandatory authoritative-observation regression

The v0.1.0 `authoritative-observation` VM scenario remains independently mandatory. It verifies that the planning milestone has not weakened:

- authenticated transport-derived caller identity;
- provider availability/capability reporting;
- native systemd observation/freshness;
- explicit NetworkManager available/unavailable behavior;
- observed provider/capability/resource/evidence graph relationships;
- deterministic evidence explanation;
- out-of-band active → inactive re-observation.

Trusted Release Proof for v0.2.0 must re-run both this regression and the plan-preview scenario before building/promoting release bytes.

## Security and resource-boundary evidence

The exact candidate must retain negative coverage for:

- malformed typed identifiers and D-Bus wire values;
- oversized semantic summary;
- excessive per-type and total semantic-origin counts;
- empty or excessive desired-state attributes;
- over-limit attribute key/value strings;
- over-limit aggregate normalized request payload;
- duplicate/conflicting desired-state keys;
- inconsistent preview status/risk/execution-authority wire representation;
- oversized retained request+preview entries;
- aggregate retained-byte exhaustion;
- deterministic count/byte eviction;
- cross-principal plan lookup/replay attempts;
- same principal/request ID with different normalized input;
- stale/future/mismatched authoritative evidence;
- unsupported/unavailable observation provider/capability route.

The failure behavior is fail-closed. Error text exposed to clients must not leak another authenticated principal's UID/namespace identity.

## Architecture-boundary review evidence

A Codex review found that the first implementation placed replay, authoritative observation, planner invocation, and retention orchestration inside `linura-dbus`. That would have forced future non-D-Bus transports to duplicate authority semantics.

The root correction moved the sequence into transport-neutral `linura-control::PlanPreviewControl` and introduced generic `AuthenticatedPrincipal` ownership. `linura-dbus` now derives authenticated D-Bus credentials/actor provenance and delegates typed requests to the control plane. Direct planner/observation orchestration dependencies were removed from the D-Bus preview path.

A subsequent Codex review found that dedicated plan-preview VM path filtering omitted `linura-core/**` and `linura-graph/**`. Both are now included so changes to core identifiers/provenance/risk or graph behavior cannot bypass the dedicated planning-system gate.

Both findings were resolved on the final implementation candidate and exact-source qualification passed afterward.

## Release-proof hardening required for v0.2.0

v0.1.0 Trusted Release Proof required only the authoritative-observation VM because that was the entire v0.1.0 claimed system capability. v0.2.0 adds a separate externally testable planning claim, so final proof must require **two** independent reusable VM jobs:

1. authoritative-observation regression;
2. Control1 plan-preview acceptance.

The isolated release build and promotion dispatch must depend on both. A successful build cannot compensate for a missing or failed planning-system acceptance job.

Repository tooling tests must pin this dependency shape so a later workflow refactor cannot accidentally remove the v0.2.0 scenario from the proof chain.

## Unsupported claims and experiment boundary

Passing this dossier qualifies only the Experimental v0.2.0 deterministic planning claim. It is not evidence for:

- production readiness;
- supported Linux distribution/hardware profiles;
- LLM/agent interpretation;
- policy/approval authority;
- Polkit/executor authority;
- public mutation/apply;
- durable prepare/commit or crash recovery;
- persistent intent/desired-state/plan/Library storage;
- post-effect verification, commit, audit, reconciliation, compensation, or rollback;
- a complete eleven-stage managed mutation;
- First Boot or Control Center as release-qualified workflows;
- fleet/enterprise remote authority.

Artifact presence, architectural placeholders, or future-facing docs do not expand the release claim.

## Release decision rule

v0.2.0 may be called an Experimental release only when every mandatory gate in `docs/releases/v0.2.0.md` succeeds for the final selected source and the protected publication lifecycle reaches successful independent published-release verification.

The decision is fail-closed:

- any mandatory failure, cancellation, missing result, or skipped mandatory job blocks qualification;
- success on an earlier source cannot override a final-candidate failure;
- prose cannot waive machine evidence;
- executor/bootstrap/update artifacts cannot expand the claim;
- a tag or GitHub Release is insufficient if it is not the exact proven immutable publication;
- publication is incomplete until the independent verifier succeeds.

## Evidence retention and auditability

VM runs retain machine-readable acceptance evidence and diagnostics according to repository artifact-retention policy. Trusted Release Proof and publication preserve release notes/evidence, source/version identity, checksums, SPDX SBOM, build-environment data, and provenance attestations.

For an audit, begin from the immutable `v0.2.0` tag/GitHub Release and the independent verification run. Follow the release source SHA back through the release-intent main gates, Trusted Release Proof, both VM jobs, isolated build and reproduction. This dossier explains the meaning of those artifacts; it is not itself the evidence store.
