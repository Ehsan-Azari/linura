# v0.1.0 qualification dossier

**Release:** `v0.1.0`
**Claim class:** Experimental
**Qualification subject:** authenticated authoritative Linux observation and causal system graph
**Decision state:** implementation qualification satisfied; final release qualification and publication evidence remain gated by the protected release lifecycle

## Purpose

This dossier defines the human-auditable qualification record for Linura v0.1.0. It connects the release claims in `docs/releases/v0.1.0.md` to reproducible acceptance scenarios and machine-generated evidence without turning prose into a second source of truth.

The authoritative evidence for a particular candidate is produced by CI, disposable-VM acceptance, Trusted Release Proof, provenance/attestation generation and independent published-release verification. This document records what must be proved, the qualification history that informed the release, the known negative cases, and the decision boundary for calling the capability Experimental.

A result recorded here never overrides a failing or missing automated gate.

## Qualification model

v0.1.0 uses five evidence layers:

1. **Static verification** — formatting, strict linting, workspace tests, repository/tooling checks and contract-history validation.
2. **Security analysis** — dependency/security audit and CodeQL on the exact candidate source.
3. **System acceptance** — exact-source binaries executed in a disposable Linux VM against native systemd and, when available, NetworkManager.
4. **Release reproducibility and provenance** — isolated release build, independent byte-for-byte reproduction, checksums, SPDX SBOM, source/version identity and attestations.
5. **Publication verification** — tag-last publication of the proven payload followed by independent re-download and verification of the public release.

The release is qualified only when every mandatory layer applicable to the final candidate succeeds.

## Mandatory positive scenarios

### Q-OBS-001 — authenticated caller identity

**Goal:** prove that Linura identifies the live local D-Bus caller from the transport boundary.

**Procedure:** start exact-source `linurad`, connect through the session Control1 interface and invoke `WhoAmI`/`linuractl whoami`.

**Pass:** a typed caller identity is returned from authenticated transport credentials; the observation path does not trust a caller-provided identity assertion.

### Q-OBS-002 — provider capability discovery

**Goal:** prove that provider availability is observable before a resource read is attempted.

**Procedure:** invoke `Capabilities`/`linuractl capabilities` in the acceptance guest.

**Pass:** systemd capability is reported from the actual provider state; NetworkManager is reported according to actual service availability; an absent NetworkManager service must be represented as `availability=unavailable` with unsupported manager capability rather than omitted or silently degraded.

### Q-OBS-003 — authoritative systemd observation

**Goal:** prove native, current observation of a controlled systemd unit.

**Procedure:** create and start the fixture unit outside Linura, then observe `systemd:unit:<fixture>` through Control1.

**Pass:** the returned envelope identifies the systemd provider/resource/capability, carries valid observation/freshness metadata and reports the unit as active.

### Q-OBS-004 — out-of-band active → inactive transition

**Goal:** prove that Linura re-reads provider state and does not substitute cached/desired state.

**Procedure:** after Q-OBS-003, stop the fixture unit externally with `systemctl`, then perform a new Linura observation.

**Pass:** the subsequent authoritative observation reports `active_state=inactive`.

This scenario also covers the systemd garbage-collection edge case: explicit observation resolves the installed unit through systemd's native `LoadUnit` path before reading Unit properties. `LoadUnit` loads the installed definition for inspection but does not start/stop the unit or modify its unit file.

### Q-OBS-005 — causal graph projection

**Goal:** prove that authoritative observation becomes attributable graph evidence.

**Procedure:** query the graph after successful observation and bind the explanation's current `evidence_id` to the corresponding evidence node.

**Pass:** the graph contains the resource, provider, capability and current evidence nodes and verifies these exact relationships: provider → capability (`provides`), resource → provider (`observed-by`), capability → resource (`realizes`) and evidence → resource (`evidence-for`).

### Q-OBS-006 — deterministic explanation

**Goal:** prove that current evidence can be explained without model inference.

**Procedure:** call `ExplainObservation`/`linuractl explain` for the observed resource.

**Pass:** the response resolves the current authoritative evidence and its provenance deterministically.

### Q-OBS-007 — NetworkManager observation when available

**Goal:** exercise the second native provider without fabricating support where the service is absent.

**Procedure:** inspect the NetworkManager provider and manager-capability blocks; when available, observe manager state through its native D-Bus provider.

**Pass:** native state is returned when available. If the service is absent, the provider entry must exist with `availability=unavailable`, a reason, and `support=unsupported` for the manager observation capability. Missing, malformed or unexpectedly degraded provider state fails the scenario rather than being reinterpreted as successful absence evidence.

## Mandatory negative and failure-path evidence

The exact candidate's canonical test suite and VM harness must continue to cover or enforce the following classes:

- spoofed/client-supplied caller identity must not replace transport-derived identity;
- malformed resource identifiers must fail closed;
- provider/resource/capability mismatches must not be accepted as current authoritative evidence;
- stale evidence must not silently replace a fresher authoritative observation;
- unavailable providers must remain explicit;
- missing or checksum-mismatched VM images must fail before guest qualification;
- explicitly requested KVM must fail before launch when `/dev/kvm` is inaccessible;
- automatic acceleration selection must not equate a present device node with usable KVM;
- premature QEMU termination must fail readiness instead of waiting for an unrelated SSH timeout;
- systemd garbage collection of an inactive unit must not make an installed explicitly named unit unobservable;
- test-fixture `sudo` authority must remain external to Linura and must not be exposed as a product mutation capability.

## Qualification defects discovered and resolved

Qualification is expected to find real defects. v0.1.0 already produced two material examples; both were corrected at their root cause rather than bypassed.

### QD-001 — inaccessible KVM mistaken for usable acceleration

**Observed failure:** the hosted environment exposed `/dev/kvm`, but QEMU failed with `failed to initialize kvm: Permission denied`.

**Cause:** presence of the device node was insufficient proof that the runner could open KVM read/write.

**Correction:** VM tooling now probes actual KVM usability; `auto` falls back to TCG when KVM is inaccessible, explicit unusable KVM fails before launch, and the workflow's hosted qualification baseline is TCG. VM readiness additionally detects early QEMU death.

**Status:** resolved and covered by the qualification harness.

### QD-002 — inactive installed unit disappeared after systemd garbage collection

**Observed failure:** initial active observation passed, but after the fixture was externally stopped the second observation failed with systemd `NoSuchUnit`.

**Cause:** the observer used systemd Manager `GetUnit`, which only resolves a currently loaded unit object. systemd may garbage-collect inactive unreferenced units even while their unit files remain installed.

**Correction:** explicit systemd observation now uses native Manager `LoadUnit` to resolve the installed unit definition before reading Unit properties. This restores read-only observation after garbage collection without starting the unit or modifying persistent configuration.

**Status:** resolved and proved by the active → inactive VM scenario.

## Final-candidate evidence binding

The final candidate is never identified by manually editing this document with a mutable branch name or copied hash. The protected release lifecycle binds the actual candidate automatically:

- PR/release checks bind to the exact Git commit SHA;
- disposable VM evidence records the exact source SHA and scenario digest;
- `VM-ACCEPTANCE-EVIDENCE.json` records base-image URL/digest, acceleration mode, tested binary digests, tool/harness versions, workflow identity and result;
- Trusted Release Proof records source/version identity and seals the built payload;
- independent reproduction verifies required binary equality;
- final publication creates the version tag only after proof and promotion;
- independent publication verification re-downloads and verifies the public metadata/assets/evidence/attestations.

A human-readable dossier therefore remains stable while the machine evidence binds each execution to immutable identities.

## Unsupported claims and experiment boundary

Passing this dossier is sufficient only for the release contract's **Experimental** observation/graph claim. It is not evidence for:

- production readiness or a supported installable Linura operating system;
- deterministic intent → desired-state planning as a supported end-to-end workflow;
- plan authorization, managed mutation or privileged execution;
- Polkit-backed production authority;
- durable prepare/commit, crash recovery, reconciliation or production audit persistence;
- the complete eleven-stage managed-mutation lifecycle;
- persistent intent lifecycle or an operational Linura Library;
- AI/LLM intent interpretation or agent authority;
- First Boot as a release-qualified user workflow;
- a supported Linux distribution, desktop, hardware tier or fleet-management profile.

Those capabilities require their own later milestone contracts and qualification evidence.

## Release decision rule

v0.1.0 may be called an Experimental release only when all mandatory evidence in `docs/releases/v0.1.0.md` succeeds for the final selected source and the protected publication lifecycle completes without bypass.

The decision is fail-closed:

- any required failing, cancelled, skipped-when-mandatory or missing gate blocks qualification;
- historical success on a different source cannot override a final-candidate failure;
- prose in this dossier cannot waive a machine gate;
- artifact presence cannot expand the release claim;
- publication is not complete until independent published-release verification succeeds.

## Evidence retention and auditability

The VM workflow retains machine-readable acceptance evidence and diagnostics as GitHub Actions artifacts according to repository retention policy. The release payload preserves release evidence, source/version identity, checksums and SPDX SBOM; GitHub/Sigstore provenance attestations bind published artifacts to their build identity.

For an audit, begin with the immutable `v0.1.0` release/tag and its published evidence, verify the independent publication-verification result, then follow source SHA and workflow identities back to the corresponding protected-main and Trusted Release Proof runs. This dossier supplies the claim/scenario map for interpreting that evidence; it is not the evidence store itself.
