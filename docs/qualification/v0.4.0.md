## Trust and authority interpretation

The v0.4 evidence proves a durable **authority transaction/recovery substrate**, not managed mutation support. `Prepared`, `Indeterminate`, `Verified`, committed metadata, transaction/generation identity, policy Allow and approval evidence remain distinct from execution authority. The repository records `executor_state = none`, `managed_mutation_support = none`, `complete_lifecycle = false` for v0.4.

Raw filesystem/database writers are not prevented from modifying bytes. Unauthorized retained-record changes fail closed because valid keyed integrity tags cannot be minted without the separately provisioned integrity key. Coherent rollback of the whole database/filesystem/VM snapshot remains unsupported without a future independent monotonic anchor/restore protocol.

## Release-preparation gate

The release-preparation PR freezes version `0.4.0`, coherent lockfile metadata, CHANGELOG/README status, this qualification dossier, `docs/qualification/v0.4.0-release-review.md`, `docs/releases/v0.4.0.md`, and release automation that reruns both v0.4 fault suites. `contracts/roadmap.toml` remains at released `v0.3.0` / next `v0.4.0` until publication is independently verified.

Every valid review finding must be corrected with permanent regression coverage where applicable and requalified on the new exact head before closure. A fresh documented exact-head adversarial review must return clean before merge.

## Publication gate

After release-preparation merge, publication remains blocked until all of the following are terminally green for the protected release source:

1. a single-parent metadata-only `release:` authorization commit whose tree is identical to its reviewed parent and whose `Reviewed-Source` / `Reviewed-Tree` trailers match exactly;
2. fresh protected-main CI, Security and CodeQL;
3. Trusted Release Proof validating release intent and independently rerunning authoritative-observation VM, Control1 plan-preview VM, v0.4 SQLite/WAL durability-fault and real ext4 ENOSPC qualification before build;
4. isolated exact-source build, independent reproduction and sealed evidence;
5. promotion of the proven sealed bytes without rebuild;
6. proof-first/tag-last immutable GitHub publication of `v0.4.0`;
7. independent Release Verification from a fresh runner.

Only after independent verification may roadmap bookkeeping advance `current_release` to `v0.4.0`, `next_release` to `v0.5.0`, mark the v0.4 milestone released and record terminal proof/publication/verification evidence.
